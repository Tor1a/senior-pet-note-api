# API 계약서: 오늘 기록 삭제 (저장 되돌리기, v1)

- 2026-10-12 신규. 기획서: `.company/plans/저장-되돌리기.md` 4-3. 기존 API 의 필드·응답은 바꾸지 않고 엔드포인트 1개만 추가한다.
- 인증: 다른 API 와 같다(`Authorization: Bearer <accessToken>`).

## 1. 일일 기록 삭제

`DELETE /api/pets/{petId}/daily-logs/{recordDate}` → **204** (본문 없음)

- `recordDate`: `YYYY-MM-DD`. 서버가 계산한 **현재 기록 날짜(새벽 4시 규칙, `app.zone` 기준)와 같아야 한다.** 지난 날짜·미래 날짜는 지울 수 없다(`PUT` 과 같은 규칙).
- 그날 기록이 **없어도 204**다(멱등). 같은 요청을 두 번 보내도, 동시에 보내도 모두 204다.
- 같은 날짜에 `PUT` 과 `DELETE` 가 동시에 겹쳐도 5xx 는 나지 않는다. 마지막 쓰기가 이기며(PUT 이 이기면 1건, DELETE 가 마지막이면 0건), PUT 은 충돌 시 서버가 최대 3회 재시도한다.
- 지우는 것은 그날의 일일 기록(`daily_logs` 1행)뿐이다. 투약 체크(`med_logs`)·알림 설정은 건드리지 않는다.
- 삭제 후 `GET /api/pets/{petId}/today` 의 `dailyLog` 는 `null`(제안값 `suggestions` 는 평소대로), 지난 기록 조회의 그날 `dailyLog` 도 `null` 이다.
- 삭제 후 같은 날짜로 `PUT` 하면 새 기록이 만들어진다(새 `id`).

## 2. 오류

| HTTP | code | 언제 |
|---|---|---|
| 400 | `INVALID_RECORD_DATE` | 날짜가 현재 기록 날짜와 다름, 날짜 형식 오류. 메시지에 현재 기록 날짜가 들어 있다 |
| 401 | `UNAUTHORIZED` | 토큰 없음·잘못됨·만료 |
| 404 | `NOT_FOUND` | 없는 반려동물 또는 남의 반려동물 (이 검사가 날짜 검사보다 먼저라, 남의 pet 은 날짜가 틀려도 404) |

새 오류 코드는 없다. 오류 형식은 `{code, message}`.

## 3. 클라이언트 주의

1. **되돌리기 전에 서버 기록을 확인한다.** 저장 직후 "되돌리기"를 누를 때 `GET /today` 로 현재 `dailyLog.updatedAt` 을 받아, 내가 저장한 응답의 `updatedAt` 과 같을 때만 삭제(또는 이전 값 PUT)한다. 다르면 다른 기기가 고친 것이므로 덮어쓰지 말고 안내한다. 저장(PUT) 응답의 `updatedAt` 은 서버가 계산한 값이 아니라 **DB 에 실제 저장된 값**(수정 시 DB 트리거가 갱신한 값)이므로, 저장 직후 `GET /today` 의 값과 문자열까지 정확히 같다(첫 저장·수정 모두. 2026-10-12 수정 전에는 수정 시 약 2ms 달랐다). 서버는 버전 검사를 하지 않는다(확인과 삭제 사이의 짧은 틈은 남는다).
2. **04시 경계.** 03:59 에 저장한 기록은 전날 날짜 기록이고, 04:00 이 지나면 그 날짜는 삭제도 수정도 할 수 없다(400 `INVALID_RECORD_DATE`). 되돌리기 시점에 날짜가 넘어갔다면 400 을 받으므로 "시간이 지나 되돌릴 수 없어요"로 처리한다. `recordDate` 는 저장 때 쓴 값이 아니라 `GET /today` 의 `recordDate` 를 쓰는 것이 안전하다.
3. 204 는 "지금 그 날 기록이 없다"는 뜻이다. 실제로 지웠는지와 원래 없었는지는 구분하지 않는다.
4. 네트워크 오류 시 같은 요청을 다시 보내도 안전하다.
